# 排版与发布

## 0. 按需路径预检（与写稿并行，结果进成稿确认卡）

不要等到最后一步才发现路走不通。用户要把文章送进微信（草稿、预览或发表）时，在写稿、排版的同时用**只读**调用
摸清这个账号能走到哪一步，结果写进成稿确认卡的「账号能力」一行，走不通的动作不放进可选项。
**互不依赖的探测并行发出**：用户没说交付终点时，`list_drafts` 和 `list_followers` 一起探（都是只读，代价很小），
这样确认卡里可以直接给出发表选项；用户明确只要本地稿时不预检。
发表与草稿分属不同权限域，以 `list_followers` 结果作参考。
图片链路不预检（上传本身就是副作用），在阶段 B 第一张图出错时按下文「上传失败时判定故障层」处理。

| 探测 | 通过意味着 | 失败意味着 |
|---|---|---|
| `weixin_core_list_accounts` | 连接正常，目标账号 `status=active` | 账号未连接或已取消授权 → 按 SKILL.md「授权与边界」 |
| `weixin_oa_list_drafts` | 草稿可读写 | 40164（白名单）或资质问题 → [recovery.md](recovery.md) |
| `weixin_oa_list_materials` | 素材可读写 | 同上 |
| `weixin_oa_list_followers` | 用户管理族有权限 | 多为 48001 → **预览（需 openid）和发表（freepublish）通常同族受限** |

三条铁律：

1. **工具在清单里 ≠ 账号有权限。** `mode=direct`（配置直连）账号的 `scopes` 为空，实际权限由微信返回决定，
   预检以实测结果为准。
2. **能写草稿 ≠ 能发表。** 草稿读写和发表分属不同权限域，很多未认证号卡在这里。预检阶段就要说清，
   不要让用户走到最后一步才被告知“发表不了”。
3. **不要继承上一次的故障结论。** 同一条链路可能上一轮 `INVALID_IMAGE`、下一轮 `40005`、再下一轮恢复正常。
   每轮任务都重新做一次轻量探测，别把历史判断当成永久结论。

错误码的完整含义与处置见 [查询与恢复](recovery.md)。

## 1. 本地迭代 → 一张确认卡 → 一次执行到底

**改稿不要动线上资源。** 用户每提一条修改意见就重新部署图床、重新上传图片、重新写一次草稿，
既浪费配额又会污染草稿箱。**也不要把一次交付拆成好几次确认**：草稿、预览、发表放在同一张成稿确认卡里一次批准。

**阶段 A（自由，可反复，不联网，Agent 自主完成）**

1. 定稿后 `scripts/build_article.py` 渲染（排版按 [layout-design.md](layout-design.md) 由 Agent 按选题设计，样式组件见 [editor-kit.md](editor-kit.md)）；
2. 生成本地预览（`check_html.py --preview` 可出 375px 手机预览），放进成稿确认卡给用户看真实版式；
3. 按 [封面与配图](imagery.md) 先定主题视觉锚点，再用 `scripts/make_visuals.py` 生成大字报封面和 2–4 张正文信息图
   （生成模型出的场景图才用 `scripts/prepare_image.py` 处理），插进正文后重新渲染；
4. 同时做第 0 节的只读预检；全部就绪后出成稿确认卡（[interaction-cards.md](interaction-cards.md) 第 3 节）。
   用户要调整就在本地改完重出这张卡，改到第 N 版都不产生任何外部副作用。

**阶段 B + C（用户选中「确认执行」后连续执行，中间不再停下来确认）**

1. 本地图走「本地图片上传」拿到上传链接（不必再部署图床），只处理这次新增或换掉的图；
2. 封面调 `weixin_oa_add_material` 取得 `media_id`；正文图用「正文图一键转存」整篇换成 mmbiz URL，
   没有该工具时逐张调 `weixin_oa_upload_content_image`；
3. 按「草稿写入与核对」写入草稿并读回，记录 `draft_digest`；
4. 用户批准里包含预览或发表时，**读回核对通过就直接继续**：带最新 `draft_digest` 调预览或发表，再查发表终态（见下文「预览」「发表」）。
   读回核对通过 = 标题、摘要、封面和正文段落与批准版一致，差异只有微信的正常改写（见「草稿写入与核对」）。
5. 任何一步失败或读回不一致就停在那一步：已完成的步骤和资源照实回报，按 [recovery.md](recovery.md) 给出可选路径，
   不跳过失败步骤去执行后面的对外动作。
6. 执行完一次性回报：草稿 `media_id`、读回校验结果、草稿临时预览链接、预览是否送达 / 发表终态。

### 已入草稿后的修改：指令即批准，不再出确认卡

用户对**已经在草稿箱里的同一篇**提出修改（改字、换标题摘要、换封面或配图、换排版），这条修改指令本身就是
「更新这篇草稿」的批准，不再出确认卡：

1. 本地改完，跑 `build_article.py`（图片改动先过 [imagery.md](imagery.md) 第四步自检），Agent 自己看过结果再继续；
2. 只上传新增或换掉的图（资源复用表），`weixin_oa_update_draft` 更新同一个 `media_id`，读回核对；
3. 一次回报：改了什么、草稿 `media_id`、读回结果、新的草稿临时预览链接，以及被替换下来、仍留在素材库里的旧素材
   （删不删由用户决定，删除仍需确认）。

边界：只覆盖「更新同一篇草稿」。发表、微信预览、删除素材或草稿等对外可见/不可逆动作仍要用户主动确认；
修改让旧的发表或预览批准失效（见「digest 规则」）。用户的指令有歧义、会改变文章立场或事实，或要动的是另一篇草稿时，
先用一张卡说清再动。

### 资源复用表（阶段 B 之后保留在对话里）

| 资源 | 标识 | 复用规则 |
|---|---|---|
| 正文图 | mmbiz URL | 同一张图不重复上传；换掉哪张才重传哪张 |
| 封面 | `media_id` | 不换封面就沿用；换封面才重新 `add_material` |
| 草稿 | `media_id` + `draft_digest` | 改文字走 `update_draft`，不新建草稿 |
| 图床目录 | 公网 URL 前缀 | 同一目录不重复部署；要改图就一次改齐再部署一次 |

只改文字 → 只 `update_draft`（新的 `idempotency_key`），图片资源全部复用。
换账号 → 复用表整表作废，回到第 0 节重新预检（见 SKILL.md「会话账号绑定」）。

### 执行前确认清单（写在成稿确认卡上，不单独再出一次）

成稿确认卡必须覆盖以下各项，用户在同一张卡上看完即可批准：

```text
- 账号：<昵称/主体>（account_id 后 6 位 …abc123）
- 动作链：上传图片 → 创建草稿 / 更新草稿 → 读回核对 →（可选）微信预览给谁 /（可选）发表
- 内容：标题…；摘要…；正文（本地预览页，入草稿后以微信读回版为准）
- 资源：封面 1 张（新传/复用）、正文图 N 张（M 张新传、K 张复用）
- 影响：发表后对外可见、不可撤回；预览会给真人发一条消息；公网部署会覆盖该目录既有线上内容
```

选项见 [interaction-cards.md](interaction-cards.md) 第 3 节：「确认执行：入草稿箱（推荐）/ 确认执行：入草稿箱并发表 / 调整 / 先不入草稿」；
发表、微信预览等对外可见动作不标推荐，由用户主动选中。已经在草稿箱里的稿子单独发表或更新时用该文件第 6 节的卡。

## HTML 约束

排版设计见 [layout-design.md](layout-design.md)，样式组件见 [editor-kit.md](editor-kit.md)。无论哪条路线产出的 HTML 都要满足：

- 使用单栏结构和内联 `style`，优先 `section`、`p`、`h2`、`strong`、`blockquote`、`ul`/`ol` 和 `img`。
- 不依赖外部 CSS、JavaScript、动画、表单、iframe、SVG、Flex/Grid 或绝对定位。微信仍可能进一步清理样式。
- 不使用事件属性、`script`、`iframe`、`object`、`embed`、`form`、`base` 或 `svg`；
  链接只使用 HTTP(S)；CSS 不使用 `url()`、`@import`、`expression` 或 `behavior`。
- 图片提供有意义的 `alt`；全文一个主强调色，颜色、粗体、大字、背景和下划线不同时堆叠。
- 最多 8 篇图文；标题最多 32 字、作者 16 字、摘要 120 字；正文最多 19,999 字且 UTF-8 体积小于 1MB。
- 以上约束由 `python3 scripts/check_html.py 成稿.html` 检查；写入草稿前加 `--final`，确认图片都已是微信图片地址。

## 图片上传

图片先按 [imagery.md](imagery.md) 生成并用 `prepare_image.py` 处理达标。上传类工具的 `image_url` 取值有两种：

- **本地图片（默认）**：走下面「本地图片上传」拿到 `upload_url`，把它作为 `image_url`；
- **已有公网 HTTPS 地址**：直接作为 `image_url`，由服务端下载。

不要把 base64 或 data URI 塞进参数，服务端不接受，也会白白消耗大量 token。

### 上传失败时判定故障层

服务端各环节的失败都体现在上传工具上，只能靠对照测试分层：已获上传批准后，
用一个第三方可信地址（如 `https://www.python.org/static/img/python-logo.png`）传一次做对照。

注意两种图片错误不同：`INVALID_IMAGE_URL` 是地址本身不合规（非 HTTPS 公网地址或带用户信息），
`INVALID_IMAGE` 是服务端取图失败或被判不安全。完整错误码见 [recovery.md](recovery.md)。

| 现象 | 说明 | 处置 |
|---|---|---|
| 第三方图也失败，报 `INVALID_IMAGE`「目标地址不安全」 | 服务端出网被拦，请求根本没到微信 | 走手动通道；不建议反复重试 |
| 第三方图也失败，报 `40005` / `40113` | 请求到了微信，服务端 multipart 组装有问题 | 同上，并把错误码+对照证据整理给用户去报障 |
| 只有我们的图失败 | 图片或托管地址问题 | 检查 magic bytes、体积、`Content-Type`、URL 是否 200 |
| 本地上传链接报 `INVALID_IMAGE_URL` | 链接过期或不是本人创建的 | 重新创建上传链接再传 |
| 本地上传链接报 `INVALID_IMAGE`「还没有收到图片」 | `curl` 没成功 | 看 `curl` 返回码，传成功再调 |

### 本地图片上传

每张图一个上传链接，逐张处理：

1. 调 `weixin_oa_create_image_upload`（只读，不需要幂等键），拿到 `upload_url`，30 分钟内有效，只限本人使用。
2. 在本机终端上传（只能 PUT 一次，一个链接只装一张图）：

   ```bash
   curl --fail --upload-file ./wx_images/图1.jpg "<upload_url>"
   ```

   返回 `{"status":"uploaded",...}` 才算成功；`413` 超限、`415` 不是有效 PNG/JPEG、`404` 链接过期、
   `409` 已经传过（换新链接）。
3. 正文图调 `weixin_oa_upload_content_image`、封面调 `weixin_oa_add_material`，`image_url` 填同一个 `upload_url`。
   有效期内同一个链接可以再次引用（比如同一张图既做正文图又做封面），过期后重新走第 1 步。

没有终端（无法执行 `curl`）的环境用不了这条路，改用下面的公网托管或手动通道。

### 正文图一键转存（`weixin_oa_localize_content_images`）

工具清单里有它时，正文图不再逐张调 `upload_content_image`：

1. 正文 HTML 里的 `<img src>` 可以是公网 HTTPS 地址，也可以是本地图走完上面第 1–2 步后的 `upload_url`。
2. 把整篇 HTML 作为 `content` 传入（带 `account_id` 和稳定的 `idempotency_key`）。服务对**每个不同的非微信图片
   上传一次**（同一地址出现多次只传一次），已是 mmbiz 的图不动；一次最多 20 张不同的图，超出就分段处理。
3. 返回的 `content` 是替换好地址的 HTML，**只改了 `src`，其余字节不变**，直接用于写草稿；
   `images` 列出每张图的 `source`、新 `url` 或 `error`。
4. **部分失败不重来**：有 `error` 的图按错误码单独处理（换图、重建上传链接）后，只把那几张再转存一次；
   成功的 URL 记进资源复用表。
5. 封面不走这个工具，仍用 `weixin_oa_add_material`。

转存前先跑 `python3 scripts/check_html.py 成稿.html`，转存后再跑一次 `--final`，确认已没有非微信图片地址。

### 托管与部署（可选）

图片已经在公网，或环境里有现成的静态托管时，也可以直接给公网 **HTTPS 地址**
（对象存储、GitHub Pages、或客户端自带的部署工具均可；不限定具体工具）。

部署属于外部副作用，三条约束：

1. **只在阶段 B 部署一次**——配图全部定稿后再部署，不每次微调都重新发布；
2. **向已有分享链接部署更新会覆盖线上内容**，部署要写进成稿确认卡一并批准，一次改齐再发；
3. 已部署过的 URL 前缀直接复用，同一张图不重复上传（见资源复用表）。

### 手动通道（图片链路不通时的兜底）

生成带 `<img>` 的完整版 HTML，在浏览器中打开，让用户全选（⌘A / Ctrl+A） → 复制 → 粘进公众号后台编辑器，
后台会自动抓取上传图片；封面在后台单独上传设置。**不要谎称图已经进草稿了。**

## 素材库管理

- `weixin_oa_get_material_count`（只读）：查看图片、图文、语音、视频素材各有多少，判断是否接近上限、要不要清理。
- `weixin_oa_list_materials`（只读）：按类型分页列出，找出要清理的 `media_id`。
- `weixin_oa_delete_materials`（**破坏性**）：一次最多 20 个 `media_id`，逐个删除，每个返回
  `deleted`（已删）/ `failed`（未删，附错误）/ `unknown`（结果未确认）。
  1. 删除前用执行确认卡列出账号、要删的素材（名称或缩略说明 + `media_id` 后 6 位）和影响：
     已被草稿或已发文章引用的封面、图片删除后会失效，**删除不可撤销**。
  2. 用户主动选中「确认删除」后执行，带稳定的 `idempotency_key`。
  3. 按状态逐条回报；`unknown` 用同一幂等键重放或用 `list_materials` 核实，不换键重删。
- 只有旧版单个删除工具 `weixin_oa_delete_material` 时，同样逐个确认、逐个回报。

## 草稿写入与核对

1. 封面 `media_id` 写入 `thumb_media_id`；正文用转存后的 HTML。
2. 新文章用 `weixin_oa_create_draft`；**同一篇文章的后续修改一律 `weixin_oa_update_draft`**
   （指定 `media_id` 和从 0 开始的文章 `index`），不反复新建草稿。
3. 每次写入都用独立稳定的 `idempotency_key`。同一请求重传保持原键和参数；内容或目标变化后换新键。
4. 写入后用 `weixin_oa_get_draft` 读回，记录 `draft_digest`。

**微信会改写 HTML，这是正常的，别误判失败：**

- `<img src>` → `<img data-src="https://mmbiz.qpic.cn/.../640?from=appmsg">`
- 可能丢掉部分 style、`alt` 被保留
- `<br>` 可能变成 `<br  />`

核对通过标准：标题、作者、摘要、封面与批准版一致，正文段落和小标题没有缺失，图片地址都变成 mmbiz 的 https 地址且仍存在。
通过后可以沿用成稿确认卡上的批准继续预览或发表；不通过就停下，把差异摆给用户重新确认。

## digest 规则

- 每次成功写入草稿，`draft_digest` 都会变化。这是写入的正常结果，**本次执行里自己写入产生的新 digest 不需要用户重新批准**，
  读回核对通过即可沿用批准。
- 批准之后内容又被改动（用户提修改、Agent 换图换封面、或草稿被别人在后台改过），旧预览和旧发表批准**全部失效**，
  重新出确认卡。
- `weixin_oa_publish_draft` 必须传最新的 `expected_draft_digest`（从最近一次 `weixin_oa_get_draft` 拿）；
  报 `CONTENT_CHANGED` 说明读回之后草稿又被改过（例如有人在后台编辑），这是防呆机制，不是 bug——
  重新读取、把差异给用户看、重新取得批准，不自动换 digest 重试。

## 预览

预览属于**对外动作**（会给真人发一条消息），接收人和账号要写在确认卡上，用户批准后才发；
可以和入草稿箱放在同一张成稿确认卡里一次批准，草稿写入并读回通过后直接发出。
草稿还没建立时只能给本地 HTML 预览，不存在“先预览再写草稿”的顺序。

1. 调用 `weixin_oa_preview_draft` 前必须明确接收人；返回 `CAPABILITY_UNVERIFIED` 表示该部署未开启预览。
2. `preview_draft` 需要 `recipient_openid`。取 openid 的顺序：`weixin_oa_list_followers` →
   若返回 48001（很常见），请用户给公众号发一条消息，再查 `weixin_oa_list_recent_messages` 取返回中的用户标识。
   两条路都拿不到，就不要猜。拿到后可用 `weixin_oa_get_follower_info`（`openids` 数组）核对是不是本人。
3. **拿不到 openid 或预览未开启时，用 `weixin_oa_get_draft` 返回的 `url`**
   （带 `tempkey` 的 `mp.weixin.qq.com/s?...`）作为预览——微信内打开可见真实排版，但要提醒**有时效**。
   同时可以在本地打开所见即所得的 HTML 给用户看版式。
4. 明确告知用户是否真的发送了微信预览，不要把本地预览说成微信预览。

## 发表

1. 发表前必须让用户看到：目标账号（昵称/主体 + `account_id` 后 6 位）、标题、摘要、封面和正文，
   并主动选中写明「发表」的确认选项。两种来源都算：
   - **新文章**：成稿确认卡上的本地预览 + 「确认执行：入草稿箱并发表」。草稿写入后读回核对通过就直接发表，
     不再拿读回版二次确认；
   - **草稿箱里已有的稿子**：先 `weixin_oa_get_draft` 读回，用 [interaction-cards.md](interaction-cards.md) 第 6 节的卡展示读回版后确认。
   批准只对用户看到的那一版内容有效，批准后内容一改就失效。
2. 调用 `weixin_oa_publish_draft`（带最新 `expected_draft_digest`），再用 `weixin_oa_get_publish_status` 查一次终态；
   还在处理中就告诉用户已提交、稍后可再查，不循环轮询。
3. 只有微信返回成功才算“已发表”。`publish_id` 只代表已提交。
4. **发表不是群发**，不承诺向所有粉丝推送。

### 发表被 48001 拦住时

账号资质限制（常见于未认证订阅号/个人主体），错误码为 `INSUFFICIENT_SCOPE`（`wechat_errcode` 48001 或 61007），
重新授权也拿不到，重试无意义。如实交付并给替代路径：

- 草稿已在草稿箱中（给出 `media_id` 和正文校验结果），用户在后台点群发即可，**效果与发表接口一致**；
- 提醒用户在后台确认封面和配图；
- 说明打通一键发表需要微信认证（个人主体不可认证，企业/组织主体 300 元/年）。

不要含糊其辞地说“已发布”，也不要让用户以为是自己操作有误。
